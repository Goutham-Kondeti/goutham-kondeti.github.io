OfficeMate-to-Barti EHR Migration

A detailed clinical informatics case study covering legacy-data extraction, data profiling, normalization, source-to-target mapping, multi-location reconciliation, validation and integration planning.

SettingMulti-location optometry
RoleClinical Informatics Analyst
Scale100,000+ source records
ToolsSSMS · Excel · EHR systems

Overview

Preparing a legacy optometry system for a safer, cleaner EHR transition.

Village Eyecare was preparing to move from OfficeMate to Barti across a multi-location outpatient eye-care environment. My role focused on the data and workflow work that must happen before a migration can be trusted: understanding the legacy system, identifying relevant records, extracting data, standardizing inconsistent values, mapping fields to the target, validating the result, and documenting integration risks.

Core challenge: the legacy export contained approximately 100,000 inventory records, while the target onboarding workbook contained only about 1,500 records. The goal was not to move everything blindly; it was to determine what was active, relevant, uniquely identifiable and ready for the target system.

Context and role

Clinical informatics beyond the patient chart.

The work involved inventory and operational data because those records directly support ordering, pricing, billing, location-level availability and staff workflows. In optometry, products also carry specialized attributes such as eye size, bridge size, temple length, frame material and frame type. A technically successful migration that loses or misclassifies these attributes can still disrupt care delivery and business operations.

Problem definition

The visible report was not the same as a migration-ready dataset.

Data-quality issues

  • Duplicate products with different names, SKUs or location-specific records
  • Missing UPCs, vendors, costs, prices and technical attributes
  • Numeric values stored as text and leading zeros at risk
  • Leading/trailing spaces and non-printable characters
  • Inconsistent product, vendor and manufacturer naming
  • Same product priced or described differently by location
  • One-to-many backend relationships creating duplicate query rows

Migration risks

  • Loading inactive or historical products into the new system
  • Incorrect target mapping causing billing or inventory errors
  • Loss of location-level quantities
  • False matches from unreliable single-field keys
  • Manual review becoming too slow and error-prone
  • Device or network workflows failing after implementation

Approach

An iterative extraction-to-validation workflow.

Understand workflows
Extract source data
Profile & normalize
Map & reconcile
Validate readiness

1. Learn the operational context

Reviewed OfficeMate modules, product creation, inventory reports, location differences, vendor/manufacturer relationships, pricing and the fields expected by Barti.

2. Compare extraction paths

Used OfficeMate reporting and administrative exports, then moved to SQL Server when front-end reports did not contain complete or consistently structured fields.

3. Investigate backend relationships

Joined generalized product, detail, type and manufacturer structures while checking for one-to-many relationships and unintended duplicate rows.

4. Normalize keys and descriptive fields

Standardized data types, preserved leading zeros, removed whitespace and hidden characters, and normalized names before matching.

5. Use layered matching rather than one key

Started with SKU, evaluated product-description matching, rejected loose partial matches that produced false positives, and moved toward combinations of SKU, name, vendor and domain review.

6. Reconcile locations and validate

Maintained location-level quantities, standardized shared master attributes, flagged price conflicts and missing mandatory fields, and performed manual sampling where rules alone could not establish correctness.

Interactive workflow

What happened at each migration stage.

Extract from the most complete source

Front-end reports were useful for location-level inventory, while administrative exports and SQL Server provided a more complete view of product master data and technical attributes.

Profile before changing data

Measured missingness, duplicates, conflicting data types, repeated identifiers, location variation and the large difference between legacy and target record counts.

Normalize without destroying meaning

Used trimming and cleaning logic, text/number checks and controlled naming standards while protecting leading zeros in UPC and SKU values.

Map with business context

Aligned product code, UPC, category, vendor, pricing and optical attributes with Barti requirements. Matching used more than one attribute when a single key was unreliable.

Validate both technically and operationally

Checked mandatory fields, duplicate conditions, logical price relationships, target formatting and location quantities, then manually sampled records where automated rules could not detect semantic errors.

Representative privacy-safe examples.

Generalized SQL extraction pattern

SELECT p.product_id, p.product_name, p.cost_amount, p.retail_amount, d.sku, d.upc, t.product_category, m.manufacturer_name FROM product_master AS p LEFT JOIN product_detail AS d ON p.product_id = d.product_id LEFT JOIN product_type AS t ON p.product_type_id = t.product_type_id LEFT JOIN manufacturer AS m ON p.manufacturer_id = m.manufacturer_id WHERE p.active_flag = 1;

Beyond data migration

Integration and workflow readiness.

Diagnostic-device workflow

Analyzed Topcon, CV-5000 and NIDEK connectivity, IP settings, shared-folder output, file-based transfer and access permissions. Direct network access worked in some cases while mapped-drive access failed, showing why integration design must account for share-level permissions and infrastructure limitations.

Considered script-based folder monitoring, scheduled synchronization and cloud transfer, alongside HIPAA, encryption, concurrency and reliability concerns.

Operational workflow

Reviewed insurance eligibility through TriZetto, A2B Verify and Anagram, recognizing that multiple services were used because coverage and plan types differed. Connected required eligibility fields to appointment-request design.

Also evaluated centralized VOIP and appointment-routing concepts to reduce missed calls, uneven location workload and fragmented patient access.
