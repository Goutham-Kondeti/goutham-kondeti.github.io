Overview

Translating the pharmacovigilance case lifecycle into a relational data model.

MedSafe SafetyDB is a fictional pharmacovigilance database design created to support adverse-event intake, safety review, medical and quality review, regulatory submission, follow-up and archival. The project connects real pharmacovigilance workflow knowledge with conceptual modeling, logical design, normalization, constraints, role-based access and Oracle SQL.

Portfolio standard: All organization names, records and examples are simulated. The design does not reproduce a proprietary commercial safety database.

Business requirements

Data rules derived from the safety workflow.

  • Document initial and follow-up adverse-event information within required operational timelines.
  • Validate patient, reporter, suspect product and adverse-event criteria before case processing.
  • Perform duplicate search before creating a new case.
  • Support multiple products and events within a case.
  • Store seriousness criteria, outcomes, causality and coded medical terminology.
  • Track workflow stage, users, edits, submission status and access permissions.
  • Allow controlled follow-up, review, submission and archive activities.

Data model

Core entities and relationships.

Case domain

CASE, PATIENT, REPORTER, EVENT, PRODUCT and SUBMISSION represent the core safety record.

Associative domain

CASE_EVENT, CASE_PRODUCT, EVENT_SER_CRITERIA and EVENT_PRODUCT_CAUSALITY resolve many-to-many relationships and preserve case context.

Security domain

USER, ROLE, JOB, SECURITY_POINT and ROLE_SECURITY_ASSIGN model role-based permissions and accountability.

Workflow alignment

The database supports the process—not just storage.

Intake and triage

Create or update the case after duplicate search and minimum-criteria validation.

Safety review

Capture patient, reporter, product, event, labs, seriousness, coding, causality and narrative information.

Medical and quality review

Provide controlled review access and workflow movement based on role and status.

Distribution and submission

Track authority, submission date, status, creator and audit information.

Follow-up and archive

Allow additional information to update the record while retaining traceability.

Oracle SQL

Representative schema implementation.

CREATE TABLE case_event ( case_id NUMBER NOT NULL, event_id NUMBER NOT NULL, event_onset_date DATE, outcome_code VARCHAR2(10), event_verbatim VARCHAR2(1000) NOT NULL, CONSTRAINT pk_case_event PRIMARY KEY (case_id, event_id), CONSTRAINT fk_case_event_case FOREIGN KEY (case_id) REFERENCES safety_case(case_id), CONSTRAINT fk_case_event_event FOREIGN KEY (event_id) REFERENCES event(event_id), CONSTRAINT fk_case_event_outcome FOREIGN KEY (outcome_code) REFERENCES event_outcome_lu(outcome_code) );

Security and governance

Access, accountability and data quality.

  • Role-to-security-point assignment supports least-privilege access.
  • Created-by and last-updated-by references preserve accountability.
  • Edit-lock concepts prevent simultaneous conflicting changes.
  • Team lead/manager override supports controlled operational recovery.
  • Country, terminology and code lookups improve standardization.
  • Audit-ready submission records support traceability.
